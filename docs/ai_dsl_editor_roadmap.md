# GraphScript AI-Friendly DSL and Editor Roadmap

> Research-driven, implementable plan for improving the DSL, AST, diagnostics, and graph editor.

## Goals

GraphScript should be usable in three equivalent ways:

1. AI writes or edits `.gs` text with low ambiguity and high-quality lint feedback.
2. A human completes the same graph visually, including large graphs with 1000+ nodes.
3. AI and human can edit concurrently through replayable commands or structured patches without losing round-trip fidelity.

The core invariant remains unchanged: text, AST, IR, editor state, and emitted text must stay structurally equivalent.

## Research Anchors

- LSP diagnostics should be treated as the shape to converge on: range, severity, code, related information, `data`, and code actions. Source: Language Server Protocol `publishDiagnostics` and `codeAction`.
- Tree-sitter is useful as a benchmark for editor parsing: incremental updates, parsing on each keystroke, and useful trees under syntax errors. This does not require replacing the current parser in phase 1.
- React Flow's performance guidance maps directly to large graph UX: avoid broad node/edge subscriptions, memoize stable components/functions, collapse large trees, and simplify expensive styles.
- FlowGram is already a reasonable canvas base because it provides free layout, fixed layout, form, variable, history, minimap, and auto-layout plugin concepts.
- Projectional editor research supports the GraphScript direction: keep a structured model as the source of truth, then project it to text and graph views instead of treating the graph as a lossy visualization.
- Visual programming surveys repeatedly point to the same scaling risk: pure visual editing becomes hard when search, refactor, grouping, and textual overview are weak.

## Phase 1: Diagnostic Model

Status: stage accepted for the current DiagnosticTarget slice. A common `Diagnostic` shape exists. Parser expected-token / unexpected-token paths and Compiler block-scope failures populate code, range, context, hint, derived diagnostic/action IDs, and structured target metadata. Web JSON/API and the Web diagnostics panel carry and render the same diagnostic shape.

Create a first-class diagnostic layer:

```cpp
enum class DiagnosticSeverity { Info, Warning, Error };

struct TextRange {
    int start_line = 0;
    int start_column = 0;
    int end_line = 0;
    int end_column = 0;
};

struct Diagnostic {
    DiagnosticSeverity severity;
    std::string code;
    std::string message;
    std::string hint;
    TextRange range;
    std::vector<TextRange> related_ranges;
    DiagnosticTarget target;
};
```

Implementation path:

- Preserve existing `Result<T, std::string>` API for compatibility.
- Add optional `DiagnosticBag` to Lexer, Parser, Compiler, Validator. Parser and Compiler now expose compatible side channels via `diagnostics()`.
- Add stable codes such as `GS_PARSE_EXPECTED_TOKEN`, `GS_SCOPE_UNKNOWN_REFERENCE`, `GS_TYPE_PIN_MISMATCH`, `GS_SCHEMA_FAN_OUT`.
- Update CLI `validate` and web state JSON to include diagnostics. Web state now includes `diagnostics`, and `/api/diagnostics` exposes session or source parse/compile diagnostics with derived diagnostic/action IDs.
- Add code-action style quick fixes where cheap:
  - create missing event
  - suggest nearest node or pin by edit distance
  - add missing graph parameter
  - remove dangling connection

Acceptance:

- A malformed `.gs` file reports line/column plus a hint. Parser expected-token and unexpected top-level token paths are covered by tests.
- A graph-scope violation reports the block kind and allowed references. Compiler scope diagnostics are covered for unknown event references and forbidden function-to-node references.
- Web UI can display diagnostic code/range/hint and uses `DiagnosticTarget` for graph, node, pin, connection, parameter, source range, cross-graph location, and inactive-graph diagnostics from `module_diagnostics`.
- Web UI quickfix command actions first establish the same target context, so cross-graph quickfix replay logs `switch_graph <index>` before the action command.
- Current evidence: `webapp/test_diagnostic_highlights.py`, `webapp/test_real_backend_diagnostic_target_smoke.py`, `evidence/diagnostic-target-quickfix-coverage-audit.md`, and `.artifact/goal/2026-06-26-graphscript-ai-dsl-editor/evidence/web-module-diagnostics-consumption-122.md`.
- Remaining roadmap: dangling-reference visual placeholders and real parameter quickfix producers can further strengthen end-to-end diagnostic coverage.

- Per-graph version counter and command id.
