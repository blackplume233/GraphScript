# 语法草稿文档要求

> 状态：草稿文档写作规范。
>
> 目的：定义 `docs/syntax/design/` 下语法草稿文档必须包含的内容。
> 本文只规定“草稿应该怎么写”，不定义具体语言语法。

---

## 与当前实现语法的边界

每份语法草稿必须明确自己的状态：

- 当前已实现语法快照
- 目标语法提案
- 已放弃的替代方案
- 迁移或归档材料

目标草稿不能暗示解析器、格式化器、投影层、编辑器或运行时已经支持该
语法。实现状态应写在 `../current/`，或写在草稿内明确标注的“实现状态”
章节。

---

## 草稿必须包含的内容

每份语法草稿都必须足够完备，让后续实现者不需要从聊天记录中反推
缺失意图。

必备章节：

1. **状态与范围**
   - 说明本文是目标、替代、实验还是归档材料。
   - 说明影响哪些文件类型，例如 `.gs`、`.d.gs`。
   - 说明哪些内容刻意不在本文范围内。

2. **语法设计思路与方向**
   - 说明这套语法的核心想法和特异点。
   - 说明为什么需要这份草稿。
   - 说明它与其他草稿的差异。
   - 说明借鉴了哪些已有语言或格式。

3. **Spec 对齐**
   - 只列出本草稿需要对齐的稳定 spec 链接。
   - 不复述、不改写、不重新定义稳定设计理念。
   - 如果草稿与稳定 spec 存在张力，只记录张力和待决问题。

4. **语法总览**
   - 给出紧凑示例。
   - 说明核心心智模型。
   - 给出主要 grammar 形状或等价结构模型。

5. **完整复杂配置示例**
   - 提供一个真实、非平凡的完整文件。
   - 覆盖 import、declaration、graph/domain 内容、metadata、command 和
     嵌套结构。
   - 示例要足以展示这套语法在较大配置中的书写体验。

6. **Command 表达**
   - 如果草稿涉及 graph、workflow、event 或其他行为连接，必须单独说明
     command 如何表达。
   - 如果草稿自称 JSON-compatible，必须说明 command 是 object、tuple、
     string 还是非 canonical 扩展。
   - 必须明确哪些 command 形式可被 formatter 输出。

7. **每种语法的详细解释**
   - 每种语法形式单独成节。
   - 每节必须有示例。
   - 解释每个语法位置的含义。
   - 标明 canonical 写法和非 canonical 写法。
   - 需要时说明该语法形式对解析、降级或定位的特殊影响。

8. **结构化等价形式**
   - 说明语法如何降到 `DocumentNode`、类 JSON 对象、图投影事实或其他
     中立表示。
   - 明确该表示是创作语法、中间表示、调试输出还是编辑器状态。

9. **Formatter 与 Canonicalization 规则**
   - 说明格式化器应该输出哪些形式。
   - 说明哪些形式只作为兼容输入或迁移糖。
   - 不展开通用源码保真原则；这些原则归 `docs/spec/` 管。

10. **实现状态**
   - 说明当前已经能 parse/project 的部分。
   - 说明哪些是目标草稿。
   - 列出已知解析器、格式化器、编辑器和运行时缺口。

11. **开放问题**
    - 尚未解决的设计选择。
    - 仍然可能成立的替代方案。
    - 需要 fixture 或 prototype 验证的边界情况。

---

## KDL 参考要求

如果草稿借鉴 KDL，必须明确说明借鉴的是哪些 KDL 思路。KDL 是一种面向
节点的文档语言，节点语义接近 XML，可用于配置、数据交换或存储：

- KDL 首页：https://kdl.dev/
- KDL 规范：https://kdl.dev/spec/

草稿应明确哪些概念被采用，例如：

- 文档是一棵节点树。
- 节点名称。
- 参数。
- 属性。
- 子节点块。
- 节点级注释或禁用节点。
- schema/query 生态作为参考

草稿也必须明确哪些内容没有采用。例如 GraphScript 可以借鉴 KDL 的文档
模型，但不采用 KDL 的完整表层语法。

---

## 禁止混入的内容

语法草稿不能承载稳定设计理念。下列内容属于 `docs/spec/`，草稿只能链接
引用，不能在草稿中重新定义：

- 人类和 AI 协作的总体目标。
- 文本真源原则。
- lossless document model 的通用要求。
- visual edit 到 text patch 的总体架构。
- Graph domain 和 serialization layer 的长期边界。
- Web editor、runtime、API 的稳定产品契约。

草稿可以记录“该语法方向如何影响这些稳定目标”，但必须写成风险、张力、
开放问题或实现状态，不能写成新的通用原则。

反过来也成立：稳定设计理念文档不能混入当前临时语法或某个草稿语法。已经
实现但仍处于迁移期的写法应放在 `../current/`；正在探索的写法应放在
`../design/`；历史写法应放在 `../archive/` 或迁移记录中。

---

## 完备性检查清单

语法草稿进入评审前，必须回答：

- 一个最小文件长什么样？
- 一个复杂文件长什么样？
- 声明怎么写？
- 图或领域块怎么写？
- 类型化项目怎么写？
- 属性怎么写？
- 命令怎么写？
- 属性标注或元数据怎么写？
- 引用怎么写？
- 哪些形式是 canonical 写法？
- 哪些形式只是兼容输入？
- 中立结构化表示是什么？
- 当前仓库里哪些部分已经实现？
- 哪些部分只是目标草稿？

如果某个答案刻意暂缓，必须写入“开放问题”。
